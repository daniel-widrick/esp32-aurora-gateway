# Aurora RS485 → WiFi gateway

ESP-IDF firmware for the Waveshare Industrial ESP32-S3 RS485/CAN board. Polls
the WaterFurnace Aurora ABC over RS-485 Modbus-RTU and serves it as a JSON API
over HTTPS. Bus and pin details are in [`HARDWARE_WIRING.md`](HARDWARE_WIRING.md).

## Build and flash

From the repo root, with [ESP-IDF v5.x](https://docs.espressif.com/projects/esp-idf/)
installed:

```bash
python tools/gen_secrets.py      # .wifi + .apikey -> main/secrets.h  (see below)
./tools/gen_certs.sh             # self-signed TLS cert -> main/certs/
idf.py set-target esp32s3
idf.py -p <PORT> flash monitor   # e.g. COM3 on Windows, /dev/ttyACM0 on Linux
```

Before the first build, provide credentials:

- Create `.wifi` in the repo root: SSID on line 1, password on line 2. Then
  `python tools/gen_secrets.py` writes `main/secrets.h` and generates a random
  API token into `.apikey`. (Or copy `main/secrets.h.example` to
  `main/secrets.h` and edit it by hand.)
- `./tools/gen_certs.sh` writes the embedded TLS cert/key.

`.wifi`, `.apikey`, `main/secrets.h`, and `main/certs/*.pem` are all gitignored.

> **Windows note:** ESP-IDF's object paths are deep enough to hit the 260-char
> `MAX_PATH` limit from a long parent directory. Keep the clone near the drive
> root (e.g. `C:\dev\esp32-aurora-gateway`).

## Layout

| File | Role |
|---|---|
| `main/aurora_modbus.c` | Modbus-RTU master: 19200 **8E1**, slave 1, FC03/FC06, one transaction at a time |
| `main/poller.c` | Background poll task + thread-safe cache, so HTTP never stalls the bus |
| `main/wifi.c` | Station mode, fast retries at boot then slow forever-retry |
| `main/api.c` | HTTPS server and JSON handlers |

## TLS

Self-signed **EC P-256** cert in `main/certs/`, generated by `tools/gen_certs.sh`
(10-year validity) and embedded at build time. EC rather than RSA because the
handshake is far cheaper on this chip. Negotiates `ECDHE-ECDSA-AES256-GCM-SHA384`.

SANs are `aurora-gateway` and `aurora-gateway.local`, and the firmware
advertises `aurora-gateway.local` over mDNS, so hostname verification can
actually succeed rather than forcing every client to disable it. Clients still
need the cert pinned or added as a trust anchor, since nothing signs it:

```bash
openssl s_client -connect aurora-gateway.local:443 -showcerts </dev/null
curl --cacert main/certs/servercert.pem https://aurora-gateway.local/api/status
```

Regenerate (also 10 years):

```bash
MSYS_NO_PATHCONV=1 openssl req -x509 -newkey ec \
  -pkeyopt ec_paramgen_curve:prime256v1 \
  -keyout main/certs/prvtkey.pem -out main/certs/servercert.pem \
  -days 3650 -nodes -subj "/CN=aurora-gateway" \
  -addext "subjectAltName=DNS:aurora-gateway,DNS:aurora-gateway.local"
```

`MSYS_NO_PATHCONV=1` matters under Git Bash — without it the shell rewrites
`/CN=...` into a Windows path and openssl rejects the subject.

## Once it's at the furnace: no USB

The board lives at the heat pump with no console and no flashing cable. Three
things exist because of that, all verified on the bench before deployment:

### OTA with rollback

Two 3 MB OTA slots. `POST` a raw `.bin` to `/api/ota`; it writes the inactive
slot, reboots into it, and the new image marks itself valid **only after WiFi
and the API are up**. If it can't, the bootloader reverts on the next reset.

```powershell
idf.py build
Invoke-RestMethod -Uri https://aurora-gateway.local/api/ota -Method Post `
  -SkipCertificateCheck -ContentType 'application/octet-stream' `
  -InFile build\esp32_gateway.bin -TimeoutSec 180
Invoke-RestMethod -Uri https://aurora-gateway.local/api/ota/status -SkipCertificateCheck
```

Bump `PROJECT_VER` in `CMakeLists.txt` for every push — with no console it's how
you confirm over the network that the image you meant to ship is the one running.

**Confirmation is deliberately tied to WiFi + API, not to a successful Modbus
poll.** Tying it to the bus would mean an unplugged RS-485 cable rolls back every
new image — making the one case where you most need remote access the one case
you can't get it. A reachable gateway reporting `bus: degraded` is a good outcome.

A `ota_start_rollback_watchdog()` task closes the other hole: the bootloader only
rolls back on a **reset**, so an image that *hangs* (boots fine, never reaches
WiFi) would sit there forever. If the image hasn't confirmed within 3 minutes it
reboots itself. Verified by pushing a deliberately broken image: unreachable for
~180 s, then it recovered to the previous slot unaided.

### Liveness supervisor

OTA rollback only guards the first few minutes after an update. Once an image is
confirmed, `supervisor.c` takes over — because a *confirmed* image that hangs had
nothing watching it, and ESP-IDF's task watchdog defaults to warn-only.

| Failure | Response | Verified |
|---|---|---|
| Worker task deadlocks / starves | Heartbeat goes stale → reboot after 60 s | Yes — hung the poll task, device rebooted at ~64 s |
| WiFi drops | Retry forever, reconnect; **no reboot** | Yes — recovered in ~6 s, uptime unbroken |
| WiFi down > 30 min | Reboot, assuming a wedged driver | Threshold only; not force-tested |
| Task hogs CPU | `CONFIG_ESP_TASK_WDT_PANIC=y` → reboot | Config change |
| Panic / crash | Reboot (`PANIC_PRINT_REBOOT`) | IDF default |

The WiFi threshold is deliberately patient. A power cut can take an AP out for
20+ minutes, and rebooting through that achieves nothing — the board should just
reconnect when the AP returns. What the 30-minute reboot catches is the case
where the AP came back and *we* didn't.

Exposed on `/api/health` as `supervisor.poller_heartbeat_age_s` and
`supervisor.wifi_down_s`.

`POST /api/debug/wifi-drop` forces a disconnect to exercise the reconnect path on
a deployed board without touching the AP. It is self-recovering by design.

### Remote log

`GET /api/logs` returns a ring buffer of everything `ESP_LOG` wrote since boot.
This is the console once there isn't one.

**Memory is fixed and cannot grow.** One `LOGBUF_SIZE` (6 KB) array in `.bss`
plus one output buffer of the same size in `api.c` — no heap, no flash, no
growth. New bytes overwrite old ones. There is nothing here for a remote caller
to exhaust; `/api/health` exposes `memory.free_heap`, `free_heap_min` and
`diag.log_bytes_buffered` so you can confirm that in the field.

The real risk with a fixed ring is not overflow but **eviction** — flooding it
to destroy the history you'd want after an incident. Two sources were found by
measurement and fixed:

| Source | Before | After |
|---|---|---|
| `esp_https_server` "performing session handshake", INFO, **one per TLS connection** | 79 of 103 lines | silenced to `ESP_LOG_WARN` |
| Auth rejections, one line each | 1 per attempt | throttled: ≤1 per 10 s with a running count |

The handshake line was the worse of the two: it needed no credentials and no
valid request, just a TCP connection. Measured after the fix — 69 unauthenticated
requests produced 4 log lines, the ring stopped filling, and boot history
survived. Every rejection is still counted in `diag.auth_rejections`; only the
logging is throttled.

`logbuf_dump()` reads the ring indices under a spinlock but copies **outside**
it — a 6 KB `memcpy` with interrupts disabled is far too long a critical section
on a device running WiFi and TLS. The tradeoff is that a task logging mid-copy
can garble the oldest bytes of the output; that is fine for a diagnostic log and
cannot overrun anything, since all indices are bounded and the output is written
strictly within `cap`.

`GET /api/logs` returns a 6 KB ring buffer of everything `ESP_LOG` wrote,
captured from boot. This is the console once there isn't one.

### Safety switches — `GET`/`POST /api/mode`

Both persist in NVS, so set them before deployment and they survive the trip.

```json
{"writes_enabled": false, "polling_enabled": true}
```

- **`writes_enabled`** defaults to **false**. `/api/setpoint` returns `403`
  until you flip it. First contact with a real furnace should observe, not act.
- **`polling_enabled`** — set to `false` and the board is electrically silent:
  it never asserts DE and never transmits. Intended for first contact, where the
  AWL is already an active master on that bus. Plug in mute, confirm nothing is
  disturbed, then enable.

## Status page

`GET /` serves a read-only dashboard — zones with setpoints, loop and
refrigerant readings, decoded fault state, and device health. It refreshes every
5 s from `/api/health` and `/api/status`.

Unauthenticated, matching the other read endpoints: it renders nothing the API
doesn't already serve openly, and it deliberately does not touch `/api/logs`,
which stays protected because the WiFi driver logs the SSID there. It exposes no
controls — changing anything still needs the API key.

Entirely self-contained in `main/www/index.html` (~8.8 KB, embedded at build
time). No CDN, no external fonts: the gateway has no internet, and neither may
whoever is standing at the furnace with a phone. Responsive and theme-aware, so
it's legible on a phone in a dark mechanical room.

The fault dictionary is the full Aurora E-code table (60 codes), so reg 25
renders as `E5 · Frze Detect FP1` with a LOCKOUT badge when bit 15 is set,
rather than a bare number. A sensor reporting the ABC's `-999.9` sentinel shows
as `—`, never as a fabricated reading.

## Authentication

Every state-changing endpoint requires a bearer token. Reads (`/api/health`,
`/api/status`, `/api/registers`, `/api/ota/status`) are open.

| Endpoint | Auth |
|---|---|
| `POST /api/setpoint` | **required** |
| `POST /api/mode` | **required** |
| `POST /api/ota` | **required** |
| `POST /api/debug/wifi-drop` | **required** |
| `GET /api/logs` | **required** — the IDF WiFi driver logs the SSID at association, so an open log endpoint discloses it |
| everything else | open |

```powershell
$key = (Get-Content .apikey -Raw).Trim()
Invoke-RestMethod -Uri https://aurora-gateway.local/api/setpoint -Method Post `
  -SkipCertificateCheck -Headers @{Authorization="Bearer $key"} `
  -ContentType 'application/json' -Body '{"zone":1,"mode":"cool","value_f":72}'
```

The key lives in the repo-root **`.apikey`** (gitignored, generated by
`tools/gen_secrets.py` if absent — 32 bytes of CSPRNG entropy, URL-safe) and is
compiled into `main/secrets.h`, also gitignored. Change it by editing `.apikey`,
re-running `gen_secrets.py`, and pushing a new image.

Two implementation details that matter:

- **The token is only meaningful because the API is TLS-only.** Over plain HTTP
  a bearer token is readable by anyone on the path; the cert and the key are one
  mechanism, not two.
- **Comparison is constant-time.** `strcmp` returns at the first differing byte,
  so its timing leaks how many leading bytes were right — enough to recover a
  token byte-by-byte given enough tries. `auth.c` always walks the full length,
  and the accumulator is `volatile` so the compiler can't reintroduce an early
  exit. Rejected tokens are never logged; a near-miss in a log is a gift.

Auth and the write switch are independent gates: a valid key against
`/api/setpoint` while writes are disabled returns `403`, not `200`.

## API

All responses are JSON with `Cache-Control: no-store`.

### `GET /api/health`

Liveness plus bus and link state. `status` is `degraded` when no poll has
succeeded in the last 15 s.

```json
{"status":"ok","uptime_s":38.05,"version":"1","idf":"v5.5",
 "wifi":{"connected":true,"ip":"192.168.1.123","rssi_dbm":-61},
 "bus":{"polls_ok":17,"polls_failed":0,"last_poll_age_s":2.15}}
```

### `GET /api/status`

Decoded furnace state from the cache. Temperatures are °F; a sensor reporting
the ABC's `-999.9` sentinel (`0xD8F1`) is rendered `null`, not a bogus reading.
`fault.code` is reg 25's low 15 bits, `fault.lockout` its bit 15.

```json
{"age_s":0.58,
 "loop":{"leaving_water_f":73,"entering_water_f":68.3,"leaving_air_f":null,
         "suction_f":null,"discharge_psi":218.2,"fp1_f":74.4,"fp2_f":52.8,
         "compressor_ambient_f":80.1,"pump_output_pct":55},
 "fault":{"code":15,"lockout":false},
 "zones":[{"zone":1,"temp_f":74,"heat_sp_f":70,"cool_sp_f":76},
          {"zone":2,"temp_f":72,"heat_sp_f":68,"cool_sp_f":72}]}
```

Returns `503` until the first successful poll.

### `GET /api/registers?start=<n>&count=<1..64>`

Raw passthrough read, straight to the wire. `502` with `modbus_exception` on
failure — exception 2 means illegal or read-only address.

```json
{"start":1110,"values":[730,683,55537,55537,938,2182]}
```

### `POST /api/setpoint`

```json
{"zone": 1, "mode": "cool", "value_f": 72}
```

Writes `21204 + 9·(zone−1)` for cooling, `21203 + 9·(zone−1)` for heating, as
°F × 10.

**The range check here is the whole point.** The ABC accepts an out-of-range
setpoint on the wire, returns no Modbus exception, and then silently declines to
apply it — keeping the prior value rather than clamping. A caller would see
success and no effect. So the firmware rejects out-of-range values itself with
`422` before anything reaches the bus:

```json
{"error":"cooling setpoint must be 54..99 F; the ABC would silently ignore this"}
```

Limits are 54–99 °F cooling (probed directly on the real unit) and 40–90 °F
heating. Two caveats the response repeats, both real:

- The write **applies on the IZ2 sync cycle (~10–20 s)**, not instantly. A
  readback sooner still shows the old value — this looks exactly like failure.
- A setpoint write is a **temporary hold**. The IZ2 schedule reasserts its own
  value later, so durable control means re-asserting on a cadence.

## Testing against the simulator

The bench simulator (`simulator/`) impersonates the ABC over RS-485, so all of the above can be
exercised with nothing connected to the heat pump:

```powershell
py -m aurora_sim --port COM4 -v --reassert-after 45     # write lifecycle
py -m aurora_sim --port COM4 --scenario cooling --time-scale 60
py -m aurora_sim --port COM4 --scenario fp1-freeze --time-scale 60
```

Both write behaviours above are modelled, so you can watch a write apply after
the sync delay and then be reasserted by the schedule — the exact lifecycle
durable control has to survive.

With a running scenario the unit cycles for real, so `/api/status` shows the
compressor loading up, the VS pump tracking it over its 50–100% band, discharge
pressure climbing from ~120 to ~215 psi, and zone temperatures oscillating
around setpoint. `fp1-freeze` drives the chronic E5 source-side freeze to
lockout, which is the only practical way to exercise fault handling in August.
See [`../simulator/aurora_sim/README.md`](../simulator/aurora_sim/README.md).
